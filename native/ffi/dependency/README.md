# libffi build and reference notes

LUI pins libffi 3.8.1 for its optional native provider and broker. CMake verifies the release archive SHA-256, `81e879c094cc5ec3186c48510c6385ac6b3e866192e8bc71a35245703757ee40`, before unpacking. An offline builder can pass the same archive using `-DLUI_FFI_ARCHIVE=<absolute path>`. The SDK distributor should include `third_party/licenses/Libffi.txt` with each component linked against the archive. The upstream release separates the license for its runtime from those for its build and test tools. [Release and source](https://github.com/libffi/libffi/releases/tag/v3.8.1) · [Runtime license](https://github.com/libffi/libffi/blob/v3.8.1/LICENSE) · [Build-tool licenses](https://github.com/libffi/libffi/blob/v3.8.1/LICENSE-BUILDTOOLS)

To build the dependency by itself, configure `native/ffi/dependency` and build target `LuiFfiDependencyBuild`. To build the module, configure `native/ffi` and build `LuiFfi`. Set `LUI_FFI_BROKER=ON` to enable the `LuiFfiBroker` executable. The module and broker share the same static C++ engine and libffi ABI.

* Windows x64 uses native MSVC and MASM. The CMake recipe selects the source files used by upstream’s MSVC Win64 build and generates the public header from upstream's versioned template. The compiler preprocesses the assembly before MASM assembles it. Clients of the static archive inherit `FFI_STATIC_BUILD`. [Upstream target selection](https://github.com/libffi/libffi/blob/v3.8.1/configure.host) · [Assembly build conventions](https://github.com/libffi/libffi/blob/v3.8.1/msvcc.sh)
* Native Linux x64 uses upstream's release configure script, the selected C compiler and GNU Make. It builds static position-independent code and generates the target headers during installation. [Upstream build instructions](https://github.com/libffi/libffi/blob/v3.8.1/README.md)

## Reference implementations

Zune’s Luau C module exposes named native functions, struct layouts, library handles, closures and memory management. Its Zig implementation retains callable and closure state and delegates code generation to libwire, pinned at `b25857e1326a6b227242a7cbe566071475db70fa`. The accompanying fixture tests dynamic loading and struct operations. LUI uses the API and tests as design references. [Pinned Zune source](https://github.com/Scythe-Technology/zune/blob/590944c07252bec4d340cdd448af6cb7c1a38a50/src/core/standard/c.zig) · [Dependency manifest](https://github.com/Scythe-Technology/zune/blob/590944c07252bec4d340cdd448af6cb7c1a38a50/build.zig.zon) · [Fixture](https://github.com/Scythe-Technology/zune/blob/590944c07252bec4d340cdd448af6cb7c1a38a50/test/standard/c/init.luau)

LuaJIT illustrates explicit C declarations and the lifetime of values and callbacks passed to C. Python's ctypes documents signature selection, native authority and callback retention. CFFI makes ownership of allocated storage explicit. Rust's libloading associates a typed symbol with its library's lifetime and places the responsibility for the declared type on its caller. These distinctions inform LUI’s typed declarations, retained dependencies and copied results. [LuaJIT FFI semantics](https://luajit.org/ext_ffi_semantics.html) · [ctypes](https://docs.python.org/3/library/ctypes.html) · [CFFI](https://cffi.readthedocs.io/en/latest/using.html) · [libloading](https://docs.rs/libloading/0.9.1/libloading/struct.Library.html)
