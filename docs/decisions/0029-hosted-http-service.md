# 0029 — Scheduler-owned hosted HTTP

## Decision

Expose `HttpServerService:CreateServer(Options)` with `network.server` alone. It reuses the private network worker, TCP bind rollback/family behavior, host loopback/port policy, bounded parser, and validated response serializer. `CreateServer` binds immediately, including port zero; `Start` begins acceptance after route registration. `Start` is idempotent, `Close` is terminal/idempotent, and finalization closes resources. No method exposes a TCP socket or backend object. No firewall change is made.

Routes are exact case-sensitive method plus encoded path, excluding the query. They must be registered before Start, reject duplicates, and cap at 128 per server. Request paths are not percent-decoded or normalized. There is no implicit HEAD fallback or dynamic matching. Unknown routes return 404. Request tables are immutable, with binary string Body, original RawTarget, Path, Method, HttpVersion, ordered duplicate-preserving Headers/Trailers, and portable endpoint tables. A string preserves immutable binary content; mutable buffers proposed in the initial design are not used for request delivery. Response Body accepts string or buffer, and Headers use the same ordered field pairs as the implemented outbound client.

The network worker dispatches only completely parsed requests through a bounded completion queue. The owner creates a scheduler coroutine for the selected handler and observes its terminal return through the internal task bridge. Supported network awaits can suspend/resume it without blocking other connections. A valid handler returns one HttpReplyOptions table. Native response materialization is protected against errors and tracks VM depth/interrupts, including table metamethods. Unhandled errors, invalid returned data, framing overrides, or response overruns produce a structured local diagnostic and generic 500 reply followed by closure. Remote replies contain no exception text or paths.

Per connection, exactly one request is handled and one response written before processing the next. Reads pause during handler execution and response writing; at most one 16 KiB read suffix is retained. This keeps response order deterministic and applies transport backpressure without concurrent pipelined handlers. Each connection accepts at most 100 requests. Persistence follows [RFC 9112 §9.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.3), within the bounded profile from decision 0027. Connection close requests and body/status exceptions are honored. There is no compression, streaming, upgrade, or TLS.

Four retained server handles and 32 hosted session/handler slots are allowed per runtime; a server defaults to 16 slots and may request 1–32. Server and raw TCP bindings share the 16-listener ceiling. Retired sessions with suspended handlers retain their slot until the underlying await completes or the runtime is destroyed, preventing repeated deadline failures from accumulating unlimited tasks. A closed retained server handle continues to count until collected. Native HTTP buffers are bounded separately from the Luau memory quota. Request and response body ceilings default to 1 MiB, configurable from zero to 8 MiB; the conservative default matches the outbound client. Parser line/header/chunk ceilings remain those from decision 0027. Generic control replies use small fixed bodies even when an application's response bound is zero.

An absolute worker deadline of 1–60000 ms (default 10000) covers idle/read, scheduler delay, handler wait, and write for each request. Expiration closes the connection. It prevents further queued dispatch or coroutine resume; it does not preempt Luau already executing. Hosts should also apply VM execution quotas for untrusted code. Close stops accepts and closes sessions, releases route references, and prevents queued or suspended handlers from resuming application code. Existing underlying awaits are allowed to finish without resuming the canceled coroutine; registry references remain retained until that completion to avoid reference reuse races. Independently spawned application tasks are not owned by the HTTP handler. Runtime destruction joins the worker and releases all tasks without callbacks.

Malformed or unsupported requests produce generic 400; parser bounds produce 413. Neither dispatches application code nor resynchronizes the connection. Limit admission failures close the excess socket. Idle/header/body/handler/write timeout closes without promising an HTTP timeout reply. Initial methods and fields are deliberately limited to the strict HTTP/1.1 profile, rather than promising the complete architecture proposal.

## Verification

Headless native-peer tests exercise server-only capabilities, loopback/port policy, Start/Close, immutable requests, binary chunked bodies/trailers, duplicate reply fields, HEAD/status exceptions, persistent pipelining with a yielding handler and owner-thread Instance mutation, generic errors, response bounds, framing rejection before routing, connection admission/request-count limits, partial-input deadlines, late completion suppression, close during an await/read, and runtime destruction. Reflection, generated definitions, and positive/negative type tests share the public contract. Windows and Linux qualification uses the same runtime tests; no UI backend support is implied.

The ninth built-in service exceeded the pinned analyzer's flat function-intersection normalization limit. Generated App types now intersect records containing one literal GetService signature each, arranged in a balanced tree. This retains precise service results and rejects unknown names/wrong-service methods without introducing `any` or raising analyzer limits. The constructor generation pattern is unchanged.
