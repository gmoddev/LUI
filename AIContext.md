# AI context for LUI

Read this before making changes. **Foundations 0, 1, and the defined Windows exit criteria for 2 are complete; Foundation 3 is in progress**. The native Luau runtime, Instance model, WinUI host, portable layout/control/input semantics, and headless conformance tests build. Foundation 0 interactive behavior was verified on 2026-09-29; Foundation 1 mapping and input passed on Windows on 2026-10-01. Foundation 2 adds a versioned primitive extension ABI, C++ host bindings, sandbox VM quotas, platform services, assets, and a self-contained Windows folder. Its published desktop qualification passed on 2026-10-01 at DPI scale 1. The CLI, isolated preview host, and VS Code development extension exist; no other platform backend exists. The [full specification](docs/SPEC.md) states the intended design; [ROADMAP.md](ROADMAP.md) gives milestone order and acceptance criteria.

## Project intent

Build a native desktop framework where ordinary Luau application code uses Roblox-like Instances, properties, signals, services, and `task` scheduling. LUI defines portable semantics and uses native platform controls. WinUI 3 is first, GTK4 follows, and macOS remains a future consideration.

## Nonnegotiable design constraints

- Keep normal public APIs independent of WinUI, Win32, GTK, native pointers, and platform event loops.
- Keep the Luau VM and UI object tree on one authoritative scheduler thread; marshal native worker results back to it.
- Make LUI's layout and lifecycle semantics authoritative across backends.
- Keep native extension compatibility at a versioned C ABI with explicit ownership and capabilities.
- Treat accessibility, input/focus, reflection, and conformance as core design work.
- Keep editor preview execution outside the VS Code extension host and treat protocol input as untrusted.
- Do not add arbitrary FFI to ordinary Luau code.

## Working method

1. Read [AGENTS.md](AGENTS.md) and the relevant spec sections before editing.
2. Choose the smallest coherent part of the current roadmap foundation; do not imply unimplemented APIs are available.
3. Define semantics and tests at the runtime boundary before coupling an API to a backend.
4. Update documentation when changing public behavior. Capture settled decisions in `docs/decisions/`.
5. State exactly what was built and verified, including platform and tooling limitations.

Foundation 0's internal C host callbacks are in `native/abi/LuiRuntime.h`. They are not the stable extension ABI described for Foundation 2. The runtime reflection table in `runtime/reflection/Schema.cpp` gates implemented classes, properties, methods, signals, and parenting, and generates `types/LUI.d.luau`, `types/schema.json`, and `docs/API.md`. See [Foundation 1 progress](docs/FOUNDATION-1.md) for current scope and remaining qualification.

Foundation 2's supported primitive extension contract is [native/abi/LuiExtension.h](native/abi/LuiExtension.h). `LuiRuntime.h` remains the internal host interface and exposes host-only capability declarations, sandbox limits, extension loading, platform callbacks, and runtime-specific extension reflection. The [C++ facade](native/host/Application.hpp) binds primitive methods and signals. Extension services are registered before the first script and do not appear in the static built-in type file. Opaque objects and raw platform handles need a later ABI; high-contrast, multi-DPI, and assistive-technology qualification remain follow-up. See [Foundation 2 notes](docs/FOUNDATION-2.md).

The Windows build checks the generated definitions with the pinned Luau type checker. Direct constructor property tables currently use `any` in overloads; annotate a table with a generated `ClassNameInit` type to statically check its fields.

The examples in the original spec are design illustrations. New code should follow the repository naming and diagnostic conventions in [AGENTS.md](AGENTS.md).

Foundation 3's CLI is in [tools/cli](tools/cli). It reuses the version 1 JSON host manifest for project scaffolding, static checking, Windows launching, packaging, and preview launching. `check` defaults to isolated Luau type analysis via [tools/typecheck](tools/typecheck), with generated LUI definitions and version 1 JSON/UTF-16 diagnostics. `--mode syntax` retains `Lui_CheckScript` compilation without execution. Analysis covers the saved entry script only; modules, unsaved buffers, and dynamic extension types remain unsupported. [tools/preview-host](tools/preview-host) runs sandboxed application Luau in a separate process and streams the authoritative runtime tree, layout, reflection schema, Luau source provenance, and source-linked runtime errors over a version 1 JSON-lines protocol. Reload destroys the old runtime and starts a new generation. [vscode](vscode) provides an Instance Explorer, read-only layout/property inspector, source navigation, runtime diagnostics, a Windows native preview launcher, and separate type Problems on open/save or **LUI: Check Types**. Type checks require workspace trust and cancel obsolete jobs; application Luau never runs in the extension host or type checker. The user visually confirmed the initial editor view on 2026-10-01; the new type Problems display remains visually unqualified. See [Foundation 3 notes](docs/FOUNDATION-3.md) and [decision 0026](docs/decisions/0026-isolated-luau-type-diagnostics.md).

Networking Foundation A is the completed Foundation 2 TCP follow-on, qualified by [Windows and Linux CI](https://github.com/gmoddev/LUI/actions/runs/37174780149) on 2026-10-03. It includes scheduler-owned yielding tasks, a pinned Asio worker, capability-gated `NetworkService`, paired dual-family listeners, host address/port policy, paced outbound family dialing, connection `Closed` signals, and headless transport tests. [Foundation A notes](docs/NETWORKING-FOUNDATION-A.md) state shipped semantics and limits. [SPEC §53](docs/SPEC.md#53-networking-and-hosted-endpoints-planned), [decisions 0022–0025](docs/decisions/0025-paced-dialing-and-closed-signal.md), and the broader [architecture proposal](docs/proposals/NETWORKING-ARCHITECTURE.md) separate implementation from planned APIs.

Networking Foundation B is complete for its defined HTTP/1.1 scope, qualified by [Windows and Linux CI](https://github.com/gmoddev/LUI/actions/runs/37187918045) at `3011c91` on 2026-10-04. Its [HTTP parser and serializers](runtime/network/http) define bounded strict framing, binary bodies, metadata trailers, and terminal errors ([decision 0027](docs/decisions/0027-bounded-http-framing.md)). `HttpService` uses only `network.client`, shared paced dialing/policy, deadlines, 32 outstanding calls/results, cancellation, and immutable responses ([decision 0028](docs/decisions/0028-outbound-http-service.md)). `HttpServerService` requires only `network.server`: CreateServer binds, Route registers exact encoded method/path handlers before Start, and Close is terminal. Reads pause during each scheduler handler/write, retaining at most a 16 KiB suffix and admitting at most 100 requests per connection. The task bridge captures handler returns and prevents queued/suspended resumes after close/expiry; underlying await references remain held until completion. Generic remote errors contain no exception text. Four retained servers, 32 session/handler slots, body limits, and total per-request worker deadlines bound resources ([decision 0029](docs/decisions/0029-hosted-http-service.md)). Executing Luau uses VM quotas rather than deadline preemption. [Foundation B notes](docs/NETWORKING-FOUNDATION-B.md) preserve the original HTTP qualification; Foundation C adds TLS. Compression decoding, streaming, JSON helpers, and outbound pooling remain absent.

Networking Foundation C's UDP slice is qualified by [Windows/Linux CI](https://github.com/gmoddev/LUI/actions/runs/37189268030) at `7fbbe5d` on 2026-10-04. Bind needs `network.raw` and `network.server`; send additionally needs `network.client`. Numeric IPv4/IPv6 datagrams, owned binary/empty buffers, one receive waiter, local send ordering, oversize rejection/recovery, and close cancellation use the shared worker/owner scheduler. Sixteen retained handles, 32 queued/active sends and 256 KiB payload per socket, and 128 shared outstanding awaits/results bound resources. The 65507-byte payload ceiling is configurable downward. Paired dual-family UDP, DNS destinations, multicast/broadcast configuration, mapped IPv6, and receive deadlines are deferred ([decision 0030](docs/decisions/0030-bounded-udp-datagrams.md)).

Foundation C now also implements private OpenSSL TLS, HTTPS clients, and hosted HTTP's Boolean `TLS` option, with all 12 Windows native suites passing; combined Windows/Linux TLS CI qualification is pending. Clients always verify chain, dates, server purpose, and original URL DNS/IP identity, with DNS SNI and no validation bypass or plaintext fallback. The size/version-checked owner-host `Lui_SetTlsOptions` parses optional exclusive PEM CA roots and explicit PKCS#12 server credentials once before scripts/network use; no secret/native handle enters Luau. Windows uses pinned static OpenSSL 3.5.9 with OS roots/Disallowed checks, Linux distribution OpenSSL 3 and system trust paths. TLS 1.2 minimum, 128 KiB certificate lists, depth eight, existing request/session quotas, handshake deadlines, bounded shutdown, cancellation, and worker-join destruction define the shipped profile. Completed framed responses settle before bounded cleanup; abrupt TLS EOF cannot finish a close-delimited response. Provider calls/host parsing are not preempted by timers. Live revocation/AIA, enterprise policy, mTLS, manifest/named credentials, direct TLS sockets, and streaming remain deferred. See [decision 0031](docs/decisions/0031-portable-tls-and-https.md), [dependency build](docs/TLS-DEPENDENCY.md), and [Foundation C notes](docs/NETWORKING-FOUNDATION-C.md). Next: cross-platform TLS exit audit, then Foundation 3 editor work.
